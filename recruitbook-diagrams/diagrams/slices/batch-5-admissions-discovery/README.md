# Batch 5 — Admissions Discovery

This folder is the frozen PlantUML + object-context packet for the fifth RecruitBook implementation slice.

**Goal:** allow an authenticated **active student** to control, on their own profile, whether it is published and whether they consent to admissions visibility; allow a **verified admissions officer** to discover and read only the profiles that are effectively visible (published AND consented), through a discovery list and a read-only per-student safe view. This is the **first admissions-officer access of any kind** — through Batch 4, `admissions_officer` has zero policies on every table.

## Goal and implementation boundary

Batch 5 adds exactly one new stored concept — student-controlled profile visibility — and exactly one new cross-role read surface — admissions discovery of profiles that are effectively visible. It does **not** add search ranking, saved lists, messaging, AI, uploads, or any new stored trust/verification labels. It does not touch the Batch 2 profile tables' shape, the Batch 3 counselor-link model, or the Batch 4 counselor-review model — those remain exactly as closed. The only write path Batch 5 introduces is the student's own visibility settings; admissions officers write nothing in this batch.

## In scope (frozen)

- New domain object / table: `profile_visibility_settings` — one-to-one with `student_profiles`, owned and written only by the student.
- Two student-controlled booleans: `is_published` and `admissions_consent`, both defaulting to `false`.
- Effective admissions visibility, computed strictly as `is_published AND admissions_consent` — never one flag alone.
- Verified admissions officer: discover (list) and read (per-student safe view) only effectively-visible student profiles. SELECT-only.
- New RLS: policies on the one new settings table + additive SELECT-only admissions policies on the four existing Batch 2 profile tables (`student_profiles`, `academic_backgrounds`, `profile_activities`, `profile_achievements`), gated on effective visibility.
- UI lands on existing/already-planned routes only: `/student/profile` (visibility controls, extending the existing edit page), `/admissions/dashboard` (discovery list — already registered for `admissions_officer + verified` since Batch 1), `/admissions/students/[id]` (read-only safe profile view, new dynamic route reusing the dashboard's guard). No route-policy changes.

## Out of scope (frozen — deferred)

Shortlists / saved students (`Shortlist`, `ShortlistEntry`) · messaging, expressions of interest, notifications · AI features or consent beyond the two visibility controls (no `AIContextualizationOutput`/`AIConsentRecord` involvement) · uploads/transcripts · free-text or narrative search (discovery is a plain list/filter over already-visible rows, not a search index) · stored `VerificationTier` or `SelfReportedLabel` objects · audit events (deferred with link/review audit, same future `SECURITY DEFINER` RPC family) · counselor-review changes of any kind (`counselor_student_links`, `counselor_review_requests`, `counselor_feedback_notes` are untouched and admissions gets zero policies on them) · route-policy redesign · any Batch 1–4 redesign · admissions officer writes of any kind · markdown/rich text / `dangerouslySetInnerHTML`.

## Security invariants and no-oracle rules

- **Effective visibility is a strict AND, computed at query time.** `is_published AND admissions_consent`. A missing settings row (student never touched the controls) is **not visible** — there is no implicit-visible default. Either flag being `false` is **not visible**. There is no partial-visibility state.
- **Withdrawal is immediate.** Flipping either flag to `false` removes admissions visibility at query time, the same way Batch 3 revocation and Batch 4 link-revocation remove counselor access immediately — no cached/derived visibility, no stored "was visible" flag.
- **Admissions access is SELECT-only**, gated on both role (`is_verified_admissions_officer()`) and effective visibility (`is_admissions_visible_profile(profile_id)`). No admissions write path exists anywhere in this batch.
- **Zero admissions access to counselor-review data.** No policy of any kind is added for `admissions_officer` on `counselor_student_links`, `counselor_review_requests`, or `counselor_feedback_notes`. This is a regression-gated absence, the same pattern that protects the Batch 3 SELECT-only boundary and the Batch 4 counselor-write boundary.
- **No existence oracle on direct profile-id guesses.** A guessed/foreign/hidden student profile id at `/admissions/students/[id]` must produce **one** generic "not available" result — indistinguishable whether the id doesn't exist, belongs to a profile that was never published, or belongs to a profile whose consent was withdrawn.
- **No count/filter oracle in discovery.** The discovery list/search must operate only over rows RLS already made visible; it must never let an admissions officer infer the existence, count, or attributes of a non-visible profile through result counts, filter behavior, or timing.
- **Student profile content stays plain text**, rendered through normal escaped JSX in the admissions safe view — no markdown, no `dangerouslySetInnerHTML`, matching every prior batch.
- **Zero service-role.** Admissions discovery runs entirely under the authenticated cookie-aware Supabase server client with RLS as the backstop, exactly like Batch 2–4.
- **Suspended students are not a visibility bypass.** A suspended student's own write access to their settings is governed the same way Batch 2 writes are (independent server-side re-check), but effective visibility to admissions is a pure function of the stored flags — Group 2 must decide and document explicitly whether a suspended student's already-published, already-consented profile should remain admissions-visible, rather than leaving it as an accidental side effect. (Recorded as an explicit Group 2 design question, not pre-decided here.)

## Proposed object / state model

**`ProfileVisibilitySettings`** (catalog concept; prototype-refined as a single table `profile_visibility_settings` for Batch 5 — see refinement note below): one row per `student_profiles.id` (nullable/absent = not visible), holding exactly two independent booleans, `is_published` and `admissions_consent`, both defaulting to `false`. There is no state machine with named transitions beyond the two booleans and their AND — Batch 5 deliberately does not build the fuller catalog `SM-6`/`SM-12` machinery (draft/incomplete/blocked-unverified-email/updated-since-last-viewed states, AI-consent interplay, shortlist rechecking) described in the master catalogs.

**Prototype refinement (decided, not drift — same pattern as Batch 3's `HighSchool` refinement).** The master catalogs model visibility/consent and admissions discovery more richly than Batch 5 needs: two separate privacy objects (`ProfileVisibilitySettings`, `ConsentSettings`), a full `SM-6` profile-publication state machine, and a full `SM-12` admissions-discovery state machine including `StudentDiscoverySearch`, `AdmissionsProfileView`, `Shortlist`/`ShortlistEntry`, and verification-tier-aware safe views. Batch 5 collapses the two privacy objects into one table with two booleans, and implements only the strict-AND visibility gate plus a read-only list and detail view — no shortlist, no search index, no verification tiers. The richer `SM-6`/`SM-12` models remain in the catalogs as the unbuilt long-term direction; the matching catalog rows will be annotated with this refinement when the catalogs are updated in a later diagram group (not in this documentation-only group).

## Schema / RLS handoff to Group 2

Group 2 implements, **after a independent schema and RLS design review, and is reviewed by independent review again after the migration is written** (the same before-and-after sequence used for Batch 3 Group 2 and Batch 4 Group 2 — the first cross-role RLS surface in each batch gets this treatment).

- **One new table, `profile_visibility_settings`** — one-to-one with `student_profiles` (`student_profile_id` NOT NULL UNIQUE → `student_profiles(id)` ON DELETE CASCADE), `is_published boolean NOT NULL DEFAULT false`, `admissions_consent boolean NOT NULL DEFAULT false`, `created_at`/`updated_at` (reuse `set_updated_at()`). No other columns anticipated (no publish timestamp, no consent timestamp, no history) unless Group 2 review decides otherwise.
- **Hardened helpers anticipated by this plan** (standard recipe: `SECURITY DEFINER` + `SET search_path = public` + `STABLE` + revoke EXECUTE from PUBLIC + grant to `authenticated`):
  - `is_verified_admissions_officer()` — mirrors `is_verified_counselor()`: caller's `application_users` row has `role = 'admissions_officer'` and `account_status = 'verified'`.
  - `is_admissions_visible_profile(profile_id uuid)` — mirrors `is_linked_counselor_for_profile()`/`is_admissions_visible_profile` in shape: `is_verified_admissions_officer()` AND a `profile_visibility_settings` row exists for `profile_id` with `is_published = true AND admissions_consent = true`, tested at query time (so withdrawal is immediate).
- **Additive SELECT-only admissions policies** on the four Batch 2 profile tables (`student_profiles`, `academic_backgrounds`, `profile_activities`, `profile_achievements`), gated by `is_admissions_visible_profile(...)` — the same additive pattern Batch 3 used for counselor SELECT-only access. Batch 2 owner CRUD, Batch 3 counselor SELECT-only, and platform_admin SELECT stay untouched.
- **No admissions policies on any Batch 3/4 table** — `counselor_student_links`, `counselor_review_requests`, `counselor_feedback_notes` get zero new policies of any kind (the deny-by-default absence is the control, verified as a regression gate at Batch 5 closure the same way Batch 3's SELECT-only boundary was re-verified at Batch 4 closure).
- **Student ownership protections for visibility settings** — student SELECT/INSERT/UPDATE own settings only, gated by the existing `is_profile_owner(student_profile_id)` pattern (reused, not redefined) plus `is_active_student()` on writes; no DELETE policy for any role; no counselor or admissions write policy of any kind on this table; `platform_admin` may get SELECT-only visibility, consistent with every prior batch. The first-write likely needs the same "bare insert, then separate owner-scoped select" pattern already recorded in `architecture-decisions.md` if a get-or-create shape is used.
- **Column-level UPDATE hardening** is not anticipated to be needed here (unlike `counselor_student_links`/`counselor_review_requests`, this table has exactly one legitimate writer — the owning student — so there is no multi-party-write column-smuggling risk the way there was for counselor accept/decline or student withdraw vs. counselor respond). Group 2 review should confirm or override this.
- **No stored derived state.** Effective visibility is never stored — it is always `is_published AND admissions_consent`, evaluated by the helper at query time, matching Batch 2's derived-completion rule and Batch 3/4's live-gate-at-query-time rule.

## Mandatory runtime gates (later Batch 5 groups — required, not optional)

1. **Verified/pending/suspended admissions-officer boundaries** — a verified admissions officer sees visible profiles; a pending or suspended admissions-officer account sees and reads nothing (route guard AND `is_verified_admissions_officer()` both deny).
2. **Unpublished / no-settings-row / consent-false exclusion** — a profile with no settings row, `is_published=false`, or `admissions_consent=false` (in any combination) is excluded from BOTH the discovery list AND a direct `/admissions/students/[id]` visit.
3. **Immediate withdrawal** — flipping either `is_published` or `admissions_consent` to `false` removes the profile from discovery and direct view immediately, with no caching lag.
4. **Guessed-id generic response** — a guessed/foreign/hidden profile id at the detail route returns the same single generic "not available" result in every non-visible case (nonexistent, unpublished, consent withdrawn) — no distinguishing response.
5. **No count/filter oracle** — discovery list/filter behavior never reveals the existence, count, or attributes of a non-visible profile.
6. **Admissions cannot read counselor data or write anything** — zero access to `counselor_student_links`/`counselor_review_requests`/`counselor_feedback_notes`; no write path exists to any table for `admissions_officer` in this batch.
7. **Cross-student settings protection** — a student cannot read or write another student's `profile_visibility_settings` row (crafted/foreign id → RLS zero-rows, generic result).
8. **Suspended-student behavior** — explicitly test and record whether a suspended student's already-published, already-consented profile remains admissions-visible, per whatever Group 2 decides and documents (not assumed either way by this packet).
9. **Hosted publish → discover → withdraw flow** — end-to-end on hosted dev: student publishes and consents, admissions officer finds and opens the profile, student withdraws either flag, admissions officer's list and direct view both lose access immediately.
10. **HTML-like content stays escaped** — profile text containing HTML-like content renders as literal escaped text in the admissions safe view, no injection.
11. **Filters, only if they ship** — if the discovery UI ships any filter/sort controls, they must be verified to operate only over the RLS-visible row set, never introducing a separate oracle path.
