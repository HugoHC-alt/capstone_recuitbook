# Batch 6 — Admissions Shortlists

This folder is the frozen PlantUML + object-context packet for the sixth RecruitBook implementation slice.

**Goal:** allow a verified admissions officer to privately save an effectively-visible student profile to a personal shortlist, see their saved students, and remove a saved entry. This is the **first admissions-officer WRITE surface** in RecruitBook — through Batch 5, `admissions_officer` has SELECT-only access and writes nothing anywhere.

This file is **Group 1a** — the frozen charter/handoff, approved by an independent planning review. **Group 1 is now COMPLETE**: the charter (1a) and all five diagrams (1b–1f, listed below, each generated and reviewed one at a time per the standing diagram-work convention) are produced, reviewed, and committed. A final independent packet review across the full Group 1 set returned **GO**. Group 1 remains planning/context only — **no schema, no migration, no TypeScript helpers, no routes, and no app code exist yet.** Admissions officers still have zero write access to anything, exactly as at the end of Batch 5. Next: **Group 2 — schema + RLS**, gated on the two prerequisites in the "Batch 5 sequencing note" below.

## Goal and implementation boundary

Batch 6 adds exactly one new stored concept — a bare officer-owned reference from a verified admissions officer to a student profile — and exactly one new admissions-facing write path: save/remove a shortlist entry. It does **not** add named/multiple shortlists, entry notes or labels, search, ranking, messaging, notifications, exports, AI, or any new stored trust/verification label. It does not touch the Batch 2 profile tables' shape, the Batch 3 counselor-link model, the Batch 4 counselor-review model, or the Batch 5 visibility-settings model or its RLS — those remain exactly as closed. The only write path Batch 6 introduces is the officer's own shortlist entries; the student experience does not change in any observable way.

## Approved planning scope (frozen at Group 1a)

- **One new table, `admissions_shortlist_entries`.** This is a deliberate prototype refinement of the master catalogs' `Shortlist`/`ShortlistEntry` pair — the same kind of collapse as Batch 3's `HighSchool` refinement and Batch 5's `ConsentSettings` collapse. Batch 6 implements **one implicit shortlist per officer**, not named or multiple `Shortlist` records. There is no shortlist name, no shortlist-level object, and no `Shortlist.create(owner, name)` surface in this batch — an officer has exactly one (unnamed) set of saved students, modeled directly as rows in `admissions_shortlist_entries`. The richer catalog model (named `Shortlist` records, each containing `ShortlistEntry` rows) remains the unbuilt long-term direction.
- **Each entry is a bare reference.** `admissions_officer_application_user_id` (server-derived, never client-supplied) to `student_profile_id` (a lookup key only). **No student profile content is denormalized into the entry** — no preferred name, no country, no any other field. Every read renders live data through the existing effective-visibility gate, never a cached copy.
- **The only user workflow:** visible profile detail (`/admissions/students/[id]`) → Save to shortlist → dashboard "Saved students" section (`/admissions/dashboard`) → Remove entry. Nothing else.
- **The Save control lives ONLY on `/admissions/students/[id]`.** There is deliberately no Save control on the discovery-list rows on `/admissions/dashboard` — saving requires having opened the detail view first. This keeps the write surface to one page and avoids a second, list-level "is this profile currently visible" check path.
- **Saved students appear only while their profile remains effectively visible.** The saved list is not a static record of "profiles I once saved" — it is a live, re-gated view.
- **Immediate disappearance on withdrawal.** If either `is_published`/`admissions_consent` flips to false, or the owning student is suspended, the entry disappears from the saved list immediately (no caching lag), and its existing `/admissions/students/[id]` URL continues to return the same generic "This student profile is not available." page that Batch 5 already established for every non-visible case. There is no distinct "you shortlisted this but it's now hidden" state anywhere.
- **Republishing resurfaces the retained entry automatically.** The underlying row is never deleted by the system when a profile becomes non-visible — only the officer's own explicit Remove deletes it. If the student later re-publishes and re-consents (and remains an active student), the same saved entry becomes visible again on the saved list without the officer needing to re-save it.
- **The student is never notified and has no observable shortlist surface of any kind.** No table, policy, page, or notification lets a student learn they were shortlisted, by whom, or when. This mirrors the master catalog's explicit `G-13` guard ("Shortlisting must not notify the student by default") and the forbidden-method entry `Shortlist.notifyStudent(...)`.

## In scope (frozen)

- New table `admissions_shortlist_entries` — one row per (officer, profile) pair, owned and written only by the verified admissions officer who created it.
- Save (idempotent) and remove actions, scoped to the caller's own entries only.
- A "Saved students" section on `/admissions/dashboard`, showing only currently-effectively-visible saved profiles using the same four minimal summary fields already approved for the discovery list.
- A "Save to shortlist" control on `/admissions/students/[id]`, alongside the existing read-only view (no change to that view's existing rendering).

## Out of scope (frozen — deferred)

Named or multiple shortlists (`Shortlist.create(owner, name)`, a shortlist-name field of any kind) · entry notes, labels, or tags · `AdmissionsOfficerProfile.expressInterest(...)` or any student-visible interest signal · messaging, notifications, or any student-facing trace of being shortlisted · search, filters, ranking, `SearchIndex`/`SearchFilter` · exports · AI features · uploads/transcripts · audit events (deferred with the link/review/visibility audit family, same future `SECURITY DEFINER` RPC) · stored `VerificationTier`/`SelfReportedLabel` · route-policy redesign · any Batch 1–5 redesign · admissions writes of any kind to `student_profiles`, `profile_visibility_settings`, `counselor_student_links`, `counselor_review_requests`, or `counselor_feedback_notes` · student or counselor access to shortlist entries of any kind · markdown/rich text / `dangerouslySetInnerHTML`.

## Security invariants and no-oracle rules

- **Zero admissions writes outside this one new table.** No admissions INSERT/UPDATE/DELETE policy is added anywhere else. `student_profiles`, `academic_backgrounds`, `profile_activities`, `profile_achievements`, and `profile_visibility_settings` keep exactly their current (Batch 2/3/4/5) policies — admissions stays SELECT-only on the profile tables and has zero policy on the settings table, unchanged.
- **Zero admissions or student access to counselor data, unchanged.** `counselor_student_links`, `counselor_review_requests`, and `counselor_feedback_notes` get zero new policies of any kind — the same regression-gated absence re-verified at every prior batch closure.
- **Zero student or counselor access to shortlist entries.** Only the owning verified admissions officer (and `platform_admin`, read-only) may ever see a shortlist row. A student can never detect, directly or indirectly, that they were shortlisted.
- **Every read re-gates on current effective visibility.** A saved entry is never a stored bypass of `is_admissions_visible_profile(profile_id)` — the same live-gate-at-query-time doctrine used by Batch 3 (`is_linked_counselor_for_profile`), Batch 4 (`is_counselor_of_live_accepted_link`), and Batch 5 (`is_admissions_visible_profile`).
- **No distinct "stale entry" state, explanation, placeholder, or count anywhere.** A hidden, unpublished, consent-withdrawn, suspended-owner, deleted, foreign, or nonexistent profile referenced by a saved entry never produces a different UI state, message, or count than "this entry currently isn't in your saved list" (it is simply absent from the live-gated list). The existing generic "not available" detail page is reused unchanged for direct-URL access — there is no new "you shortlisted this but it's gone" message.
- **No existence oracle on save/remove.** Saving a hidden or nonexistent profile id fails with the same fixed generic error as any other save failure. Saving an already-saved profile succeeds with the same fixed generic success message (idempotent — a unique-constraint violation is treated as success, not surfaced as an error). Removing a foreign, stale, or nonexistent entry id matches zero rows and returns the same generic result as a successful removal of a real entry — no distinction.
- **Cross-officer protection.** An officer can never read, save into, or remove another officer's shortlist entries. A crafted/foreign entry id or a forged owner id must be rejected by RLS, not by application logic alone.
- **Student profile content stays plain text.** The saved-students list reuses the same four already-approved minimal summary fields, rendered through normal escaped JSX — no markdown, no `dangerouslySetInnerHTML`.
- **Zero service-role.** The shortlist surface runs entirely under the authenticated cookie-aware Supabase server client with RLS as the backstop, exactly like every prior batch.

## Proposed data / RLS model — for mandatory Group 2 ratification

The following is the Group 1a **proposal**, not yet implemented or reviewed at the schema level. It requires the mandatory pre-migration design review (the same before-and-after sequence used for Batch 3/4/5 Group 2 — the first admissions WRITE surface in the system) before any migration is written.

- **Table `admissions_shortlist_entries`:**
  - `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
  - `admissions_officer_application_user_id uuid NOT NULL REFERENCES application_users(id) ON DELETE CASCADE` — server-derived at insert (never client-supplied as authorization proof); the owner.
  - `student_profile_id uuid NOT NULL REFERENCES student_profiles(id) ON DELETE CASCADE` — a bare lookup key; no student content is denormalized onto this row.
  - `created_at timestamptz NOT NULL DEFAULT now()`
  - `UNIQUE (admissions_officer_application_user_id, student_profile_id)` — one entry per officer per profile.
  - **No `updated_at` and no update trigger.** Entries are immutable except for owner hard-delete — there is nothing on this row for any role to ever update.
- **No new SQL helper is planned.** The design reuses, unchanged: `is_verified_admissions_officer()` and `is_admissions_visible_profile(profile_id)` (both Batch 5), and `current_application_user_id()` (Batch 1/2). No `is_own_shortlist_entry(...)`-style helper is anticipated — ownership is a direct column comparison, and visibility is the existing Batch 5 helper.
- **RLS policy matrix (proposed):**
  - **SELECT — owning verified officer:** `admissions_officer_application_user_id = current_application_user_id() AND is_admissions_visible_profile(student_profile_id)`. The visibility gate lives inside the SELECT policy itself, so a stale entry is structurally invisible at the database layer — no application-layer filtering can get this wrong.
  - **SELECT — `platform_admin`:** read-only, consistent with every prior table.
  - **INSERT — verified officer, own row, currently-visible profile only:** `WITH CHECK (admissions_officer_application_user_id = current_application_user_id() AND is_verified_admissions_officer() AND is_admissions_visible_profile(student_profile_id))`. An officer can only ever shortlist a profile that is visible to them right now, and can never write another officer's owner id.
  - **UPDATE — deliberately absent for every role**, plus a table-wide `REVOKE UPDATE ... FROM authenticated` (stronger than Batch 5's column-grant approach — this table has no legitimately-updatable column at all).
  - **DELETE — SUPERSEDED by a post-Group-1a design amendment; preserved below as the historical Group 1a proposal.** The original proposal was: `USING (admissions_officer_application_user_id = current_application_user_id() AND is_verified_admissions_officer())`, deliberately NOT visibility-gated, so an officer could remove an entry whose profile has since become hidden. **This could not be implemented as written.** Local adversarial testing at Group 2 proved (via `EXPLAIN` and a from-scratch minimal probe table) that Postgres implicitly ANDs a table's SELECT policies into every DELETE's row-targeting scan, regardless of the DELETE policy's own `USING` clause — so the visibility-gated SELECT policy would silently veto the DELETE policy before it was ever consulted, and a stale (hidden) owned entry could never actually be reached. A focused independent design-amendment review ratified the fix, implemented in the committed migration: the direct DELETE policy is dropped entirely and DELETE privilege is revoked from `authenticated`; removal instead goes exclusively through a hardened `SECURITY DEFINER` function, `public.remove_own_admissions_shortlist_entry(entry_id uuid)`, which bypasses RLS internally (RLS is `ENABLE`d, not `FORCE`d) and re-implements the SAME authorization intent directly in its own `WHERE` clause — ownership (`admissions_officer_application_user_id = current_application_user_id()`) AND `is_verified_admissions_officer()`, with visibility deliberately absent — so a stale entry stays removable exactly as originally intended, via a different mechanism. A foreign, stale, or nonexistent entry id is a silent no-op inside the RPC, returning the same fixed generic success as a real removal. This is the repo's first mutation RPC and the reference implementation for a new durable pattern: UPDATE/DELETE row-targeting requires SELECT-policy visibility; when a mutation must reach rows the SELECT policies hide, use a hardened `SECURITY DEFINER` RPC.
  - **No policy of any kind for `student` or `counselor`** — the deny-by-default absence is the control, the same pattern that protects the Batch 3/4/5 boundaries.
- **Duplicate save is idempotent.** A unique-constraint violation (`23505`) on INSERT is mapped to the same fixed generic success message as a genuine new save — never surfaced as an error, never distinguished from a first save.
- **No stored derived/cached state of any kind** — effective visibility is always recomputed by `is_admissions_visible_profile(...)`, exactly as it is for the discovery list and the detail view. There is no "was visible when saved" flag and no stored staleness indicator.

## Mandatory runtime gates (later Batch 6 groups — required, not optional)

1. **Save → appears in Saved students.** Saving a currently-visible profile results in it appearing in the officer's own "Saved students" section with the correct four summary fields.
2. **Duplicate save is silently idempotent.** Saving an already-saved profile produces the same generic success, with no duplicate row and no error.
3. **Immediate disappearance on withdrawal.** Flipping either `is_published`/`admissions_consent` to false, or suspending the owning student, removes the entry from the saved list immediately, with no caching lag — while its existing `/admissions/students/[id]` URL continues to return the unchanged generic "not available" page.
4. **Republish resurfaces the retained entry.** If the profile becomes visible again later (re-publish/re-consent, or the student is reactivated), the previously-saved entry reappears in the saved list automatically, without the officer re-saving it.
5. **Remove works, and removing a stale/foreign/nonexistent entry id returns the same generic result** as removing a genuine entry — no distinction, no oracle.
6. **Cross-officer protection.** An officer cannot read, save into, or remove another officer's shortlist entries — crafted/foreign entry ids and forged owner ids are rejected by RLS.
7. **Role/status boundaries.** A pending or suspended admissions-officer account has no saved list and cannot save or remove anything (route guard AND `is_verified_admissions_officer()` both deny).
8. **Zero student-visible trace.** The student side of the application shows no notification, no indicator, and no way to detect that they were shortlisted, at any point in the flow.
9. **No raw Supabase/Postgres errors** anywhere in the save/remove/list paths.
10. **HTML-like content stays escaped** in the saved-students summary rendering, matching every prior batch.
11. **Closure regression gates**, re-verified at Batch 6 closure exactly as at every prior batch closure: the Batch 3 counselor SELECT-only boundary on the four profile tables; the Batch 4 counselor-write confinement to the two review tables; and the Batch 5 boundaries — admissions SELECT-only on the profile tables, zero direct access to `profile_visibility_settings`, and zero admissions access to any counselor/review/feedback table.
