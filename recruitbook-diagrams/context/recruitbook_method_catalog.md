# RecruitBook Method Catalog

This file defines the approved method and operation catalog for RecruitBook UML, PlantUML, and AI-assisted development context.

Use this file together with:

* `context/recruitbook_object_catalog.md`
* `context/recruitbook_relationship_catalog.md`
* `context/diagram_rules.md`
* `context/security_rules.md`, if available

The purpose of this file is to define what major objects do, what inputs they require, what they return, and what security or validation rules apply.

---

# 1. Method Catalog Rules

* Use object names exactly as written in `context/recruitbook_object_catalog.md`.
* Use method names consistently across diagrams.
* Do not invent new methods unless the user explicitly approves them.
* Keep methods focused on domain behavior, not tiny UI actions.
* Use methods to support class diagrams, sequence diagrams, activity diagrams, and state machines.
* Security checks should be written explicitly in the method rules.
* Methods that expose student data must reference `AccessPolicy`, `ProfileVisibilitySettings`, `ConsentSettings`, or `RowLevelSecurityPolicy` when relevant.
* Methods that expose AI output must reference `AIOutputPolicy`.
* Methods involving transcript files must reference `FileValidationRule`.
* Methods involving privileged actions should trigger `AuditLogEntry`.
* This is a design catalog, not final production code.

---

# 2. Method Signature Format

Use this format:

```text
ObjectName.methodName(parameterName: Type): ReturnType
```

Example:

```text
UserAccount.register(email: string, password: string, role: Role): EmailVerificationToken
```

If a method does not return a value, use:

```text
Void
```

If a method may return multiple objects, use:

```text
List<ObjectName>
```

If a method updates object state, describe the state change in the security/validation rules.

# 5a. Counselor–Student Consent Link Methods (Batch 3 — Counselor Connection Foundation)

Prototype refinement of the school-match model: counselor visibility is granted by an accepted `CounselorStudentLink` (per-student consent), not by `HighSchool` match. `AccessPolicy.requireAcceptedLink(...)` is the prototype analogue of `AccessPolicy.requireSameHighSchool(...)`. All writes run under the caller's authenticated session with RLS as the backstop; no service role. Row IDs from forms are lookup keys only.

| Method Signature                                                                                     | Input Parameters & Types                                  | Return Object / Type   | Explicit Security / Validation Rules                                                                                                                                                                                                   | Source Use Case |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |

# 6a. Counselor Review Workflow Methods (Batch 4 — Counselor Review Workflow)

Prototype refinement of UC-4 counselor support: a plain-text review/feedback exchange gated end-to-end on a **live accepted `CounselorStudentLink`** (SM-13 stays the consent authority). This is the first counselor WRITE surface; every write targets the two Batch 4 objects — never the Batch 2 profile tables. All writes run under the caller's authenticated session with RLS as the backstop; no service role; row IDs from forms/routes are lookup keys only; failures surface as one fixed generic message (no oracles, no raw DB errors).

| Method Signature                                                                                     | Input Parameters & Types                                  | Return Object / Type   | Explicit Security / Validation Rules                                                                                                                                                                                                   | Source Use Case |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| `CounselorReviewRequest.submit(student: ApplicationUser, link: CounselorStudentLink, studentMessage?: string): CounselorReviewRequest` | `student: ApplicationUser`; `link: CounselorStudentLink` (id as lookup key); `studentMessage?: string` | `CounselorReviewRequest` | Requires an active student who OWNS the link and the link is `Accepted` (`is_student_owner_of_accepted_link(link_id)`). Party ids copied from the link row, never from the form. Forced `status='requested'`; at most one active request per link; `studentMessage` trimmed, ≤1000, plain text. Bare INSERT (no chained select). | Batch 4         |
| `CounselorReviewRequest.withdraw(student: ApplicationUser): CounselorReviewRequest`                  | `student: ApplicationUser` (+ request id as lookup key)   | `CounselorReviewRequest` | Requires the owning student; USING `status='requested'`; WITH CHECK forces `status='withdrawn'` + `withdrawn_at`. | `CounselorReviewRequest.decline(counselor: ApplicationUser): CounselorReviewRequest`                 | `counselor: ApplicationUser` (+ request id as lookup key) | `CounselorReviewRequest` | Requires the **addressed** verified counselor with a **live** accepted link (`is_counselor_of_live_accepted_link(link_id)`); CAS `requested → declined`; zero rows ⇒ generic error.                                                     | Batch 4         |
| `CounselorReviewRequest.complete(counselor: ApplicationUser, feedbackText: string): CounselorReviewRequest` | `counselor: ApplicationUser`; `feedbackText: string` (+ request id as lookup key) | `CounselorReviewRequest` | Requires the **addressed** verified counselor with a **live** accepted link. # 11. Methods To Avoid or Treat Carefully

These methods should not be generated unless the user explicitly approves them.

| Avoided Method                                            | Reason                                                                          |
| --------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `AdmissionsOfficerProfile.editStudentProfile(...)`        | Admissions officers should not modify student profiles.                         |
| `AIService.publishToAdmissionsView(...)`                  | AI service must not directly publish output to admissions views.                |
| `StudentProfile.uploadOfficialTranscript(...)`            | Students should not upload their own official transcript as verified evidence.  |
| `Shortlist.notifyStudent(...)`                            | Shortlisting is private and should not notify the student by default.           |
| `StudentProfile.setVerificationTier(...)`                 | Students should not directly control their verification tier.                   |
| `AdmissionsProfileView.renderWithoutAuthorization(...)`   | All admissions profile rendering must pass authorization and visibility checks. |
| `AIContextualizationOutput.replaceNarrativeResponse(...)` | AI output must not replace original student-authored content.                   |
| `CounselorProfile.viewAnyStudentProfile(...)`             | Counselors should only access students linked to their verified high school.    |
| `Database.queryProfilesWithoutRLS(...)`                   | Database access should enforce row-level security for student profile access.   |
| `UploadedFile.storeWithoutValidation(...)`                | Transcript files must pass validation before storage.                           |

# 12. Method Catalog Maintenance Rules

When the object catalog changes:

1. Check whether the new object needs methods.
2. Add only methods that support use cases, misuse cases, diagrams, or implementation clarity.
3. Avoid tiny UI-only methods.
4. Keep method names short, clear, and consistent.
5. Add explicit security and validation rules for every method that touches sensitive data.
6. Update related sequence diagrams if a method affects message flow.
7. Update related state machines if a method changes object state.
8. Update `security_rules.md` if a method enforces or depends on a security rule.
