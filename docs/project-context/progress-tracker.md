### Deferred Production Hardening Notes — Sign-Up Flow

Reviewer approved the Group 3 sign-up flow after the service-role patch. Two non-blocking hardening items were identified:

1. `actions.ts` currently treats any Postgres `23505` unique-violation error as an already-registered user success case. ### Deferred Production Hardening Notes — Admin Approval & Suspension

Group 6 is complete: `app/admin/actions.ts` (approve/suspend server actions) and `app/admin/dashboard/page.tsx` (queue UI). Three independent reviews (security, architecture, final) approved it with no critical issues. Non-blocking items recorded for later hardening:

1. **Denial is deferred.** No `decision: 'denied'` write path exists; the `approval_decision_type` enum's `denied` value is unused this group. There is no `denied` account_status (correctly — `unauthorized`/`denied` are not stored states). A future group should design the denial flow deliberately against the frozen state machine rather than improvising a transition here.

2. **Approval is non-atomic across three writes**: the `approval_decisions` insert, the CAS `account_status` update (`pending_approval` -> `verified`), and the `audit_log_entries` insert are three separate calls, not a single transaction. Each step fails closed, but a failure after an earlier step succeeds can leave inconsistent-but-safe state (see items 3 and 4 below). Future hardening: wrap the decision insert + status update (and ideally the audit insert) in a `SECURITY DEFINER` database function/RPC so they commit atomically.

3. **Audit completeness gap on partial failure.** If the `application_users` status update succeeds but the subsequent `audit_log_entries` insert fails, the action returns a generic `error` notice even though the approval/suspension already took effect — the durable authorization state is correct, but the audit trail is missing that entry and the admin sees a misleading failure message. Should be closed by the same atomic RPC, or a best-effort retry/backfill path.

4. **Possible duplicate decision rows under concurrent approval.** If two admins approve the same pending target at nearly the same time, both can pass the pre-check and insert an `approved` `approval_decisions` row before the CAS status update runs; only one CAS succeeds (the other returns zero rows -> `stale`), but both decision rows persist. This is benign over-recording on an append-only, admin-only ledger (no incorrect grant results — the CAS is the sole authority over `account_status`), but it is a data-quality nit worth eliminating via the same atomic RPC.

Group 7 is complete: a minimal, Supabase-managed password reset flow. Deferred hardening notes:

1. **`redirectTo` origin derivation trusts request headers when `NEXT_PUBLIC_SITE_URL` is unset.** The fallback builds the origin from the `origin`/`x-forwarded-proto`/`x-forwarded-host`/`host` headers, which a proxy could spoof. 2. **Password strength is only a minimal length check (>= 8).** The action enforces a length floor and equality of the two fields; Supabase Auth enforces its own password policy on top. If a stronger explicit policy is later desired, add it in `updatePasswordAction` and/or Supabase Auth settings.

3. **Callback `next` allowlist must stay restricted.** `ALLOWED_NEXT_PATHS` is currently `{ /reset-password, /login }`. If more post-auth destinations are added later, confirm the allowlist stays tight and continues to reject absolute URLs, protocol-relative paths, and unknown internal paths (all fall back to `/login`).
